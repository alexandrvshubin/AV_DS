# Avito DS

## Задача

Для каждого поискового запроса необходимо найти до 50 объявлений из `benchmark_items.parquet`, которые соответствуют смыслу запроса. Основная метрика — Recall@50.

Решение построено как двухэтапная система. Сначала формируется достаточно широкий набор кандидатов несколькими независимыми способами поиска. Затем кандидаты объединяются и дополнительно ранжируются обученной моделью.

## 

Поисковые запросы в задаче короткие. Поэтому одного текстового совпадения недостаточно: нужное объявление может быть сформулировано другими словами, а небольшая разница в написании может помешать обычному поиску.

По этой причине используются сразу три типа поиска.

Первый — BM25. Он подходит для случаев, когда важные слова запроса непосредственно встречаются в тексте объявления.

Второй — символьный TF-IDF. Он используется для более устойчивого поиска при изменениях формы слова, опечатках и небольших различиях в написании.

Третий способ — семантический поиск с помощью модели intfloat/multilingual-e5-base. Она преобразует запрос и объявления в числовые векторы. Для каждого запроса находятся объявления с наиболее близким вектором. Поиск выполняется с помощью HNSW-индекса.


Каждый метод формирует свой список кандидатов. Затем эти списки объединяются с помощью Reciprocal Rank Fusion (RRF). Для каждого объявления учитывается его позиция в каждом списке, после чего позиции объединяются в единый итоговый порядок.
Для каждого объявления рассчитывается итоговый RRF-скор:

$$
RRF(d) = \sum_{m=1}^{M} \frac{1}{k + r_m(d)}
$$

где $r_m(d)$ — позиция объявления $d$ в выдаче метода $m$, а $k$ — константа, предотвращающая слишком большой вклад первых позиций. Если объявление отсутствует в выдаче конкретного метода, его вклад от этого метода равен нулю. После расчёта скоре объявления сортируются по убыванию RRF.

После объединения списков кандидатов для каждой пары «запрос — объявление» рассчитываются признаки. По этим признакам `LightGBM` определяет порядок кандидатов внутри каждого запроса. После этого объявления сортируются по полученному значению score, и выбираются первые 50.


## Алгоритм работы

Полный алгоритм проходит следующие стадии.

Сначала выполняется нормализация текстов запросов и объявлений.

Затем для объявлений строятся индексы BM25, символьного TF-IDF и HNSW. Для HNSW предварительно рассчитываются эмбеддинги с помощью intfloat/multilingual-e5-base.

Для каждого запроса выполняются три вида поиска: BM25, символьный TF-IDF и поиск по эмбеддингам. Дополнительно используются расширение терминов запроса и данные из истории.

Результаты этих методов объединяются. Для каждого полученного кандидата затем рассчитывается набор признаков: результаты отдельных методов поиска, семантическое сходство, текстовые совпадения и признаки.

На этих признаках обучается LightGBM LGBMRanker. Обучение выполняется по группам, где одна группа соответствует одному запросу. Модель рассчитывает score для каждого кандидата, после чего кандидаты внутри группы сортируются по этому score.

После обучения модель применяется к кандидатам benchmark-запросов. Кандидаты сортируются по итоговому score, и для каждого запроса сохраняются первые 50 объявлений. Результат записывается в `answer.csv`.

## Разделение train и validation

Для обучения и проверки используется разделение по нормализованному тексту запроса. Одинаковый запрос целиком относится только к одной из выборок, поэтому запросы с одним и тем же текстом не попадают одновременно в train и validation.

Для оценки используется `Recall@50`.

Результат проверяется на отложенной выборке и не используется при обучении модели.

## Модели и обучение

Для получения векторных представлений используется готовая модель intfloat/multilingual-e5-base. На данных задачи она не обучается.

Для финального ранжирования используется LightGBM LGBMRanker с objective="lambdarank". Обучение выполняется на группах кандидатов, сформированных для отдельных запросов. Для каждого кандидата известна бинарная метка: 1 для релевантного объявления и 0 для остальных кандидатов.
В качестве метрики при проверке ранжировщика используется `NDCG@50`.

## Структура проекта

`src/avito_retrieval/data.py` отвечает за загрузку и подготовку исходных таблиц.

`src/avito_retrieval/text.py` содержит нормализацию и подготовку текстов, используемых различными способами поиска.

`src/avito_retrieval/embeddings.py` отвечает за загрузку `multilingual-e5-base` и получение эмбеддингов запросов и объявлений.

`src/avito_retrieval/indexes.py` строит и загружает поисковые структуры для BM25, символьного TF-IDF и HNSW.

`src/avito_retrieval/retrieval.py` выполняет генерацию кандидатов различными способами и объединяет результаты поиска.

`src/avito_retrieval/query_expansion.py` отвечает за расширение терминов запроса.

`src/avito_retrieval/features.py` формирует признаки пары «запрос — объявление», которые передаются в модель ранжирования.

`src/avito_retrieval/ranker.py` содержит обучение и применение `LightGBM LGBMRanker`.

`src/avito_retrieval/evaluation.py` содержит расчёт Recall@50 и других показателей, используемых для проверки решения.

`src/avito_retrieval/pipeline.py` описывает последовательность подготовки данных, обучения и формирования итогового решения.

`src/avito_retrieval/cli.py` является точкой входа для запуска обучения и получения итогового файла.

## Конфигурация и воспроизводимость

Все параметры запуска вынесены в YAML-конфигурацию. В ней задаются пути к данным, параметры моделей, размеры выборок, параметры поиска и расположение каталога с артефактами.

Для управления окружением используется `uv`. В проекте зависимости описаны в `pyproject.toml`, а их конкретные версии зафиксированы в `uv.lock`.

`uv` здесь используется именно как инструмент управления проектом: одной командой создаётся и синхронизируется окружение, а запуск приложения выполняется через то же окружение. 

Для установки окружения выполнить:

```bash
uv sync
```

Для полного запуска решения:

```bash
uv run avito-retrieval --config configs/config.yaml run --output answer.csv
```

Эта команда запускает pipeline: подготовку данных, построение необходимых индексов, обучение ранжировщика при отсутствии актуальной модели и формирование `answer.csv`.

Промежуточные результаты и обученная модель сохраняются в `artifacts`, поэтому уже рассчитанные этапы при повторном запуске могут быть переиспользованы.
